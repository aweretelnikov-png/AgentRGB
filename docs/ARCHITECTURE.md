# Архитектура AgentRGB

## Общая схема

```text
Codex ─┐
       ├─> адаптеры источников ─> нормализованные сообщения ─> реестр сеансов
Pi ────┘                                                       │
                                                               ├─> агрегатор активности
                                                               └─> контроллер временного сигнала
                                                                        │
                                                    политика индикации <─┘
                                                            │
                                                    контракт вывода
                                                            │
                                      выходной адаптер ─> RGB-устройство
```

## Модули

### Адаптеры источников

Каждый адаптер подписывается на структурированные события своего агента и выпускает нормализованные сообщения AgentRGB. Он отвечает за:

- сопоставление внешних идентификаторов с `source`, `source_instance_id`, `session_id` и `run_id`;
- разделение жизненного цикла сеанса и активного запуска;
- отделение подтверждённого окончания активности от необязательной классификации исхода;
- преобразование подтверждённых внешних событий;
- проверку версии и обязательных полей;
- отказ от передачи содержимого диалога.

Во всех документах `source` означает тип интеграции, например `codex` или `pi`, а `source_instance_id` — конкретный экземпляр процесса или адаптера. Другой общий идентификатор источника не вводится.

Адаптер выпускает только те семантические события, которые способен подтвердить надёжно. Неподдерживаемое состояние допустимо пропустить. Для постоянной активности адаптер обязан подтверждать и её окончание: источник без надёжного `run_ended` не выпускает `run_started` и не включает постоянный `working` по одному кандидату начала. Таймер не служит доказательством того, что пользователь ответил или что источник перешёл в другое семантическое состояние.

Адаптер не вычисляет общее состояние и не управляет RGB.

### Входной контракт

Текущий Pi adapter отправляет сообщения best-effort через `POST http://127.0.0.1:8765/v1/events` с deadline 200 мс, без retry и ACK. Транспортное сообщение содержит:

| Поле | Назначение |
|---|---|
| `schema_version` | Версия логической схемы сообщения AgentRGB. |
| `event_id` | Идентификатор события для транспортной дедупликации и диагностики. |
| `source` | Тип источника, например `codex` или `pi`. |
| `source_instance_id` | Идентификатор процесса или экземпляра интеграции. |
| `session_id` | Стабильный идентификатор сеанса источника. |
| `run_id` | Идентификатор логического запуска, если применимо; не обязательно идентификатор отдельного хода источника. |
| `kind` | Тип нормализованного сообщения. |
| `timestamp` | Момент возникновения события у источника. |
| `metadata` | Технические поля из явно документированного allowlist. |

Минимальные типы `kind`:

- текущий профиль Pi: `run_started`, `run_waiting`, `run_resumed`, `run_ended`.

`session_opened` и `session_closed` остаются понятиями общей модели, но текущий Pi adapter их не отправляет, а Core их не принимает.

`run_ended` сообщает только, что логический запуск больше не активен. Общая модель допускает необязательный исход `completed`, `interrupted`, `error` или `unknown`. Текущий профиль Pi сериализует в `metadata.outcome` только `completed` или `unknown`; другие исходы Core для него отклоняет. Отдельных `run_completed`, `run_interrupted` и `run_error` нет.

Ядро всегда снимает активность указанного запуска по корректному `run_ended`; исход влияет только на решение о временном терминальном сигнале. Отсутствие классификации не является неполным сообщением и не мешает переходу в `idle`. Каждый источник поддерживает только доказанные классификации. События и поля конкретного агента, включая `agent_settled` и `stopReason` Pi, остаются внутри его адаптера и не входят в общий контракт.

Pi adapter создаёт UUID для каждого логического `run_id`; `session_id` берётся из Pi. Идентификатор сеанса или индекс хода нельзя автоматически считать идентификатором логического запуска. Общий контракт не требует такого же алгоритма от будущих источников.

Требования к контракту:

- локальная доставка;
- явная версия;
- ограниченный размер сообщения;
- отсутствие запросов, ответов и транскриптов;
- устойчивость к повторной доставке и событиям не по порядку;
- возможность различать несколько сеансов и последовательные запуски одного сеанса;
- безопасный отказ при неизвестной версии или неполном сообщении;
- диагностика разрыва связи без генерации семантического `error` агента.

`event_id` используется для транспортной дедупликации, но одной дедупликации по нему недостаточно. Адаптер и ядро должны учитывать идентичность сеанса, запуска, тип события, уже принятое окончание и его исход, если он известен. Повтор `run_ended` не завершает новый запуск; один логический `run` не должен создавать несколько пользовательских терминальных сигналов из-за повторной доставки или повторного представления одного факта. Конфликтующие реальные исходы обрабатываются детерминированно; точное правило будет выбрано после исследования последовательностей источников. Сообщение без достаточного набора идентификаторов не должно молча создавать новое состояние.

Семантика и наличие `sequence` не фиксируются до прототипа: возможности источников могут различаться.

`metadata` строится по списку разрешений (allowlist): каждый разрешённый ключ и его техническая цель должны быть заранее описаны. В `metadata` запрещены:

- текст пользовательского запроса;
- ответ модели;
- содержимое файлов;
- произвольные локальные пути;
- аргументы команд и инструментов, если они не нужны для явно документированной технической цели;
- секреты.

### Реестр сеансов

Реестр хранит техническое присутствие сеанса отдельно от состояния его текущего запуска. Открытый сеанс без активного запуска имеет `idle`. Закрытие сеанса удаляет его из реестра после обработки незавершённого запуска по явно заданной политике; оно само по себе не создаёт `completed`.

По `run_ended` реестр завершает соответствующий логический запуск независимо от исхода. Позднее событие ожидания завершённого запуска не возобновляет его; окончание старого запуска не снимает активность нового.

Для каждого сеанса достаточно хранить:

- идентификаторы источника и сеанса;
- текущее постоянное состояние `idle`, `working` или `waiting`;
- идентификатор текущего запуска;
- номер или время последнего принятого события;
- техническую доступность интеграции для диагностики.

### Семантическое состояние и доступность источника

Состояние агента и техническая живость источника — независимые измерения. Концептуально реестр хранит:

- semantic state: `idle | working | waiting`;
- source availability: `available | unavailable | unknown`.

Имена будущих типов могут измениться, но разделение обязательно. Если источник подтверждённо потерян, ядро:

- не создаёт `completed` или `error` агента;
- перестаёт считать прежнее `working` или `waiting` достоверным постоянным состоянием;
- пересчитывает агрегированное состояние без устаревшего значения;
- записывает техническую проблему в диагностику.

Механизм обнаружения потери и восстановление актуального состояния после переподключения определит прототип. Возраст `working` сам по себе не доказывает потерю источника: задача может выполняться долго, поэтому произвольный тайм-аут для семантического сброса запрещён.

### Агрегатор активности

Агрегатор рассматривает только постоянные состояния сеансов:

```text
если есть waiting → waiting
иначе если есть working → working
иначе → idle
```

В агрегацию входят только значения, которые всё ещё считаются достоверными. Состояние подтверждённо недоступного источника исключается. Неизвестная доступность не позволяет автоматически возвращать устаревшее состояние в агрегат.

Активность соответствующего запуска снимается по `run_ended`, а не по наличию терминального сигнала. `completed`, `interrupted` и `error` передаются контроллеру временного сигнала и не входят в агрегат. `unknown` или отсутствие исхода не создают сигнала и не удерживают активность.

### Контроллер временного сигнала

Контроллер принимает надёжно классифицированные исходы завершённых запусков и управляет не более чем одним текущим сигналом. Неизвестный исход не поступает как пользовательский сигнал. Первая версия не содержит очереди отложенных сигналов: AgentRGB показывает актуальную потребность во внимании, а не историю событий.

Простая политика MVP:

- переход общего состояния в `waiting` немедленно прекращает текущий временный сигнал;
- терминальное событие, поступившее при активном `waiting`, не показывается и не откладывается;
- в остальных состояниях временный сигнал показывается ограниченное время;
- после сигнала политика заново читает агрегированное состояние, а не возвращается к устаревшему эффекту;
- конкурирующие терминальные факты одного запуска обрабатываются детерминированно, а точное правило выбирается после исследования реальных последовательностей.

### Политика индикации

Ядро владеет логикой времени и приоритетов. Оно хранит текущее агрегированное состояние, запускает временный сигнал, задаёт его длительность, отменяет его и решает, какая индикация актуальна сейчас. Политика преобразует это решение в команду абстрактному выходу. Она знает о цветах и эффектах, но не знает протокол конкретного выхода или модель устройства.

### Контракт вывода

Выходной модуль концептуально поддерживает операции:

1. `acquire` — проверить устройство и подготовить логическое владение AgentRGB;
2. `show_activity` — показать постоянную индикацию AgentRGB;
3. `show_signal` — показать временный сигнал;
4. `resume_activity` — применить заново актуальную индикацию AgentRGB после сигнала;
5. `release` — прекратить управление устройством и освободить ресурсы.

`acquire` не означает гарантированную эксклюзивную аппаратную блокировку. Для первой проверенной конфигурации допустимы одно выбранное RGB-устройство и требование, чтобы другое приложение не перезаписывало его подсветку одновременно. Для volatile Direct Mode снимок пользовательского профиля не требуется.

Контракт должен быть идемпотентным там, где это возможно. `release` вызывается при переходе общего состояния в `idle`, если нет временного сигнала, а также при штатном завершении AgentRGB. AULA F75 прекращает Direct-кадры, дожидается worker и закрывает handle; контроллер сам возвращает исходную статичную разноцветную подсветку после своего timeout. Это наблюдалось в D2, production H5–H7 и сквозном 04C на проверенном устройстве; аварийное завершение процесса такой возврат не гарантирует.

Выходной адаптер применяет переданную индикацию и выполняет техническое взаимодействие с OpenRGB или устройством. Он не имеет собственной очереди бизнес-сигналов, независимых таймеров семантических эффектов или машины приоритетов.

Выходной адаптер использует только экспериментально подтверждённое подмножество возможностей устройства и не обязан полностью моделировать внутренний профиль периферии. Детали транспорта и протокола конкретного устройства не расширяют основной выходной контракт.

### AULA F75 Direct Adapter

Первая реализация выходного контракта напрямую управляет AULA F75 по USB через проверенный vendor HID-интерфейс. Адаптер изолирует все сведения о `VID/PID`, HID collection, report ID, opcodes, offsets и структуре аппаратного профиля: ядро и политика индикации их не знают. Универсальная HID-абстракция для MVP не проектируется.

При `acquire` адаптер проверяет `258A:010C`, `MI_01/COL06`, usage `FF00/0001`, feature length 520, объявленный report ID `06`, а по одному свежему `0x82` — model `03` и PSD `00CD`. Текущий пользовательский config/RGB не служит gate. Один worker отправляет только 520-байтовые `0x06/0x08` Direct-кадры: 122 одинаковые RGB-тройки, остальные байты по формату D2. При активном `working` это синий, `waiting` — жёлтый, `completed` — зелёный; кадры повторяются с целевым интервалом 50 мс. Переход состояния атомарно меняет цвет worker и не создаёт второго worker. При `release` отправка прекращается, worker завершается, handle закрывается. Ни `release`, ни обработчик ошибки не посылают restore/disable или дополнительный кадр.

Для подготовки H7 добавлена приватная точка после успешного Direct-кадра. В production она ничего не делает; только экспериментальный наследник может внедрить программную ошибку вне HID transport. Такая ошибка останавливает worker и закрывает handle без restore. Core сохраняет семантическое состояние и принимает события; повторный acquire не выполняется в рамках того же run.

Persistent-путь `0x04/0x0A` в H2 показал визуальный сбой release несмотря на побайтное совпадение читаемых `0x84/0x8A`; экспериментальный backend сохранён в `experiments/phase-04b`. D2 на той же F75 подтвердил синий Direct-режим и самостоятельный возврат исходной статичной разноцветной подсветки через несколько секунд после остановки 40 кадров, без restore/disable и power cycle. Затем H5 подтвердил полный production-цикл `working → waiting → working → completed → idle`: 176 кадров через один worker, визуально все четыре цвета и самостоятельный возврат исходного профиля без restore. H6 подтвердил штатный shutdown `EventServer → Core.close → AulaF75Output.release` через `KeyboardInterrupt`: 57 кадров, 0 записей после stop, worker, handle и listener закрылись, профиль вернулся сам. H7 подтвердил controlled software fault после 20 успешных Direct-кадров: worker остановился, handle закрылся, Core и listener продолжили обрабатывать события, затем пользовательский профиль вернулся сам. [04C](../experiments/phase-04c/RESULTS.md) подтвердил полный цикл реального Pi → extension → localhost HTTP → Core → `AulaF75Output` → F75: 608 Direct-кадров, 33,900 с `waiting`, штатное завершение и самостоятельный возврат исходного профиля.

### Адаптер OpenRGB

Будущий `OpenRGB Output Adapter` реализует тот же контракт вывода через локальные возможности OpenRGB. Он будет отвечать за подключение, выбор устройства, преобразование абстрактного эффекта в доступные режимы и best-effort-восстановление.

Экспериментально установлено, что стабильный OpenRGB 1.0 не обнаружил целевую AULA F75 `258A:010C` по USB. Поэтому OpenRGB не входит в обязательный путь MVP.

Ошибки OpenRGB и устройства отправляются в диагностику. Они не создают `run_ended` или исход `error` агента и не меняют семантическое состояние его сеанса.

### Диагностика и управление процессом

Текущая диагностика Core фиксирует вид нормализованного события, исход, результат обработки и технические ошибки, без текста запросов, ответов или транскриптов. Полный мониторинг потери транспорта и восстановление состояния после переподключения не реализованы.

Пакет устанавливается через `pyproject.toml` с build backend `setuptools`, без runtime-зависимостей. Console entry point `agentrgb` вызывает `agentrgb.cli:main`. Команда `start` передаёт выбранный `--output` существующей `server.main(argv)`; запуск и завершение Core остаются общими с `python -m agentrgb.server`. По умолчанию выход — `fake`, процесс работает в текущем терминале до `Ctrl+C`.

Все команды CLI и Pi extension используют `AGENTRGB_PORT`, по умолчанию `8765`. Сервер слушает только `127.0.0.1`. `GET /health` возвращает `{"status":"ok","service":"agentrgb"}` без пользовательских данных; обработчик не обращается к Core или выходному адаптеру и не создаёт событий. `status` проверяет этот ответ прямым loopback HTTP-запросом без прокси из окружения. `running` означает доступность HTTP Core и даёт код `0`; отказ соединения (`not running`), чужой ответ или недоступность (`unavailable`) дают код `1`. Health не подтверждает исправность RGB-выхода.

`doctor` проверяет версию Python, версию установленного пакета, импорт production-модулей, доступность Core, порт и identity F75. Проверка устройства изолирована в `outputs/aula_f75_diagnostics.py` и использует существующие HID transport и identity helpers: точный интерфейс, report ID `06`, model `03`, PSD `00CD`. Она открывает единственного подходящего кандидата, выполняет identity read (`SetFeature` для `0x82`, затем `GetFeature`) и закрывает handle. Direct-кадры и команды изменения RGB/profile не отправляются; Windows HID path не выводится.

Успешный `doctor` возвращает `0`; отсутствие обязательных компонентов, ошибка импорта или identity read, отсутствие/неоднозначность/несоответствие F75 либо занятый чужим процессом или недоступный порт — `1`. Незапущенный Core при свободном порте не считается ошибкой. Ошибки аргументов CLI, включая неверный `AGENTRGB_PORT`, возвращают `2`.

Pi package (`integrations/pi/package.json`) объявляет extension, не запускающий ресурсы в factory. `session_start` проверяет health и при необходимости вызывает CLI с `--output aula-f75`. Startup ограничен пятью секундами после первого health-запроса; каждый запрос ограничен 300 мс, polling interval — 100 мс. До готовности и после ошибки события пропускаются без очереди. Существующий Core не становится собственностью Pi.

Для дочернего запуска extension задаёт только в окружении child `AGENTRGB_PARENT_STDIO=1` и создаёт приватные stdin/stdout pipes. После успешного bind сервер печатает `AGENTRGB_READY`; это подтверждение владения именно своим listener, в дополнение к `/health`. Закрытие stdin вызывает `server.shutdown()` из отдельного потока; прежний context manager выполняет `Core.close()` и освобождение output. Обычный ручной CLI без этой переменной работает как раньше. Контракт событий, state machine и hardware lifecycle не меняются; HTTP-команда остановки не добавлена.

На `session_shutdown` отправка событий прекращается и собственному child закрывается stdin. Ожидание — до 1,5 с, затем best-effort принудительная остановка только собственного child (на Windows — дерева console launcher) и ожидание ещё до 1,5 с. В startup race проигравший child выходит, после чего здоровый Core принимается как внешний. Чужой Core не останавливается. Общего multi-client ownership и supervisor нет: выход Pi-владельца может отключить индикацию остальных Pi. При принудительном завершении штатное освобождение output не гарантируется.

Координатор процесса запускает модули и отвечает за упорядоченное завершение: прекратить приём новых сообщений, завершить или отменить временный сигнал, вызвать `release`, затем закрыть транспорт и диагностику.

### Невмешательство в источник

Интеграции отправляют события по принципу best effort. Если AgentRGB не запущен, приёмник недоступен, OpenRGB отключён, устройство отсутствует или выходной адаптер завершился ошибкой, Codex и Pi продолжают работу.

Источник не ждёт завершения RGB-анимации, не повторяет отправку, не меняет решение о разрешении и не управляет продолжением агента ради AgentRGB. Pi transport использует localhost HTTP с deadline 200 мс и максимумом восьми незавершённых отправок; событие может потеряться.

## Структура первой реализации

Реализованные модули:

```text
pyproject.toml                 # Установка Python-пакета и console entry point.
integrations/pi/agentrgb.ts    # Нормализация Pi и best-effort HTTP.
integrations/pi/core.ts        # Bounded startup, ownership и shutdown дочернего Core.
src/agentrgb/cli.py            # Команды start, status и doctor.
src/agentrgb/protocol.py       # Валидация входного профиля.
src/agentrgb/state.py          # Реестр запусков, агрегирование и сигнал.
src/agentrgb/server.py         # Локальный HTTP и запуск Core.
src/agentrgb/fake.py           # Выход по умолчанию.
src/agentrgb/outputs/          # AULA F75 и Windows HID.
tests/                         # Software regression suite.
```

## Направление зависимостей

```text
app → sources ─┐
               ├→ core contracts
app → outputs ─┘
```

Ядро не импортирует адаптеры. Адаптер Codex не знает о конкретном выходе, а выходные адаптеры не знают, какое внешнее событие породило команду индикации.

AgentRGB наблюдает за агентами, но не входит в контур управления их выполнением. Это архитектурный инвариант.
