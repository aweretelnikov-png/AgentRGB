# Интеграции источников

Этот документ фиксирует соответствие структурированных событий источников модели AgentRGB. Для Pi учтены реальные результаты фазы 02; раздел Codex остаётся предварительным и в этой фазе не исследовался. События, поля и поведение зависят от версии источника.

## Общие правила

- Используются только структурированные события и поля источника.
- Показываются только состояния, которые источник позволяет подтвердить достаточно надёжно; неполная поддержка лучше ложного сигнала.
- Текст запросов, ответов и транскриптов не анализируется и не пересылается.
- Событие жизненного цикла сеанса не считается запуском.
- `run_ended` завершает активность независимо от известности исхода. Необязательный исход `completed`, `interrupted` или `error` позволяет показать терминальный сигнал; `unknown` или отсутствие классификации не создают сигнала.
- `completed` означает обычное окончание выполнения, а не успешность задачи. Источник не обязан поддерживать все терминальные классификации.
- `error` создаётся только при явном структурированном признаке ошибки запуска агента.
- Ошибка интеграционного кода или доставки сообщения относится к диагностике AgentRGB.
- Таймер не служит доказательством ответа пользователя или выхода из `waiting`.
- Недоступность AgentRGB не должна влиять на выполнение источника; отправка событий работает по принципу best effort.

## Codex

Актуальная документация Codex Hooks перечисляет события `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PermissionRequest`, `Stop` и `Interrupt`. `PermissionRequest` возникает перед запросом одобрения, а `Interrupt` — при пользовательском прерывании активного хода в основном потоке. Форматы и покрытие должны проверяться на поддерживаемой версии Codex.

Источники:

- [Codex Hooks](https://developers.openai.com/es-419/docs/hooks)
- [Codex advanced configuration](https://developers.openai.com/es-419/docs/config-file/config-advanced)

### Предварительное соответствие

| Событие Codex | Сообщение AgentRGB | Уверенность | Примечание |
|---|---|---|---|
| `SessionStart` | `session_opened` | Подтверждено документацией, проверить поля | Регистрирует сеанс. Не означает `working`. Причины запуска и возобновления нельзя считать новым активным ходом. |
| `SessionEnd` | `session_closed` | Подтверждено документацией | Закрывает сеанс. Не означает `completed`. Нужно проверить поведение при аварийном завершении процесса. |
| `UserPromptSubmit` | кандидат на `run_started` | Требует прототипа | Событие подтверждает отправку запроса, но нужно проверить, достаточно ли его для начала фактического запуска и есть ли более точное событие в используемом интерфейсе Codex. |
| `PermissionRequest` | кандидат на `run_waiting` | Не подтверждено | Codex собирается запросить разрешение, но другой hook может автоматически разрешить или запретить действие. Событие само по себе не доказывает, что пользователь увидел запрос и Codex ждёт ответа. |
| окончание ожидания разрешения | кандидат на `run_resumed` | Не установлено | Не предполагается отсутствующее универсальное событие. Нужно экспериментально найти надёжно связанную пару начала и окончания ожидания в выбранном интерфейсе Codex. |
| `Stop` | кандидат на `run_ended` с исходом `completed` | Требует прототипа | `Stop` срабатывает при остановке активного хода, но hook способен запросить продолжение. Сигнал `completed` можно выпускать только после подтверждения окончательной остановки, не анализируя текст ответа. |
| `Interrupt` | `run_ended` с исходом `interrupted` | Подтверждено документацией, требует прототипа | Срабатывает при пользовательском прерывании активного хода основного потока; не срабатывает для неактивного потока и субагентов. |
| структурированное событие ошибки запуска | кандидат на `run_ended` с исходом `error` | Не установлено | В проверенной документации hooks не найдено однозначное универсальное событие ошибки всего запуска. До подтверждения адаптер не должен генерировать `error`. |
| `PreToolUse` / `PostToolUse` | нет прямого перехода | Подтверждено документацией | События отдельных инструментов не определяют состояние или результат всего запуска. Ненулевой код инструмента не равен исходу `error` агента. |

Codex также поддерживает `notify`, но актуальная документация конфигурации описывает только `agent-turn-complete`. Это может быть запасным каналом завершения, однако он не покрывает полную модель и требует сравнения с hooks на Windows.

Точный `waiting` для Codex считается неподдержанным, пока прототип не подтвердит и начало, и окончание реального ожидания пользователя. Если выбранный интерфейс Codex не даёт обоих надёжных событий, адаптер первой версии не поддерживает `waiting`. Таймер или факт появления `PermissionRequest` не заменяет это подтверждение.

## Pi coding agent

Проверена версия **`@earendil-works/pi-coding-agent 0.85.1`**: Windows, Node.js `v24.15.0`, CLI/TUI, print и минимальный JSON-опыт; в модельных опытах использовался настроенный `openai-codex/gpt-5.5`. Основание — [RESULTS.md фазы 02](../experiments/pi-events/RESULTS.md), включая узкий опыт stopReason и очищенные сырые последовательности. Выводы экспериментально подтверждены именно для этой версии и проверенного окружения, а не для всех провайдеров и расширений.

Расширение Pi подходит для наблюдения внутри обычного CLI. Производственный адаптер и транспорт ещё не реализованы. Результаты опытов имеют приоритет перед обновляемой документацией latest; справочные источники:

- [Pi Extensions](https://pi.dev/docs/latest/extensions)
- [Pi JSON Event Stream Mode](https://pi.dev/docs/latest/json)

### Подтверждённая активность и модель логического запуска

| Событие Pi | Сообщение AgentRGB | Уверенность | Примечание |
|---|---|---|---|
| `session_start` | `session_opened` | Подтверждено опытом | Регистрирует сеанс, не включает `working`. |
| `session_shutdown` | `session_closed` | Подтверждён штатный выход | Не означает `completed`; resume/fork не проверялись. |
| `input`, `before_agent_start` | нет начала активности | Подтверждено опытом | Перед обычным запуском на них `isIdle=true`; дополнительный input внутри активного запуска не создаёт новый запуск. |
| первый `agent_start` вне активного логического запуска | `run_started` → `working` | Подтверждено опытом | `isIdle=false`; начало периода активности. |
| повторный `agent_start` до `agent_settled` | нет нового логического запуска | Правило по коду Pi; повторный start в реальном retry не воспроизводился | Автоматическое продолжение относится к текущему логическому запуску. |
| `ui_prompt_start` при активном логическом запуске | `run_waiting` → `waiting` | Подтверждено опытом | Блокирующий вызов через `ctx.ui`; в проверенном активном опыте — `custom`. |
| `ui_prompt_start` вне запуска | нет перехода | Подтверждено idle-опытом | UI-диалог сам по себе не создаёт `waiting`. |
| парный `ui_prompt_end` при всё ещё активном запуске | `run_resumed` → `working` | Подтверждено опытом | Закончился период блокирующего UI-ожидания, не обязательно вследствие ответа пользователя. |
| `agent_end` | нет окончания активности | Подтверждено опытом | На нём `isIdle=false`; сохраняется только кандидат причины текущего низкоуровневого запуска. |
| `agent_settled` | `run_ended` | Подтверждено опытом | Снимает `working/waiting`; `isIdle=true`. Сам по себе не классифицирует исход и не означает `completed`. |
| `tool_result.isError=true` | нет прямого перехода и исхода `error` | Подтверждено опытом F | Агент продолжил работу и завершился с последним stopReason=stop. |

События ожидания покрывают блокирующие вызовы через `ctx.ui` (`select`, `confirm`, `input`, `editor`, `custom` по API). Обычный текстовый вопрос модели не считается подтверждённым `waiting`. Поздний `ui_prompt_end` после окончания запуска не должен вновь включать `working`. По коду Pi окончание UI-ожидания приходит через finally, а начало доставляется микрозадачей: событие не доказывает ни ответ пользователя, ни точный момент отрисовки диалога. Вложенные prompts и гонки ещё не проверены.

### Необязательный исход при окончании запуска

Для первой версии разрешён только `completed` при следующем сочетании:

```text
последний assistant последнего низкоуровневого запуска: stopReason=stop
                           ↓
                    agent_settled
                           ↓
             run_ended с исходом completed
```

Это правило подтверждено в A (обычный ответ) и F (инструментальная ошибка, после которой агент продолжил работу). В F причины assistant были `toolUse → stop`: промежуточный stopReason не является терминальной причиной. `completed` означает только обычный способ окончания выполнения, без оценки успешности задачи.

На `agent_end` выбирается последний assistant **данного низкоуровневого запуска**, а не последний элемент массива вообще: им может оказаться toolResult. При новом низкоуровневом `agent_start` в том же логическом периоде прежний кандидат больше не считается финальным; следующий `agent_end` заменяет его. Отсутствующее или неизвестное значение нельзя подменять ранним `stop`. Окончательное решение принимается только после `agent_settled`; при разрыве наблюдения или недостоверных данных — исход `unknown`.

**`interrupted` в первой версии не поддерживается.** Реальный ручной Escape до инструмента дал `aborted`, а во время работающего инструмента — `error`. StopReason не содержит инициатора отмены; его нельзя надёжно преобразовать именно в пользовательское прерывание.

**Run-level `error` в первой версии не поддерживается.** Финальный `error` реально получен после ручного Escape, поэтому безусловное соответствие `stopReason=error → ошибка запуска` ложно. Независимая от отмены ошибка всего запуска экспериментально не проверена. `tool_result.isError=true` также не является её доказательством.

Для `aborted`, `error`, `length`, `toolUse`, `pending`, `deferred`, отсутствующего или неизвестного stopReason активность всё равно снимается по `agent_settled`, но исход остаётся `unknown` и терминальный сигнал не создаётся. Имена stopReason не становятся состояниями ядра.

### Приватность stopReason

Из AssistantMessage разрешено извлекать только структурированный enum `stopReason`; `role` читается лишь как дискриминатор для выбора assistant. В общий контракт передаётся нормализованный исход, а не объект сообщения или Pi-специфичное поле. Запрещено передавать в AgentRGB `content`, thinking, `errorMessage`, текст запросов, аргументы и результаты инструментов. Разрешённые значения stopReason для 0.85.1: `pending`, `stop`, `length`, `toolUse`, `error`, `aborted`, `deferred`.

### Идентификаторы, продолжения и границы проверки

`sessionId` идентифицирует сеанс, а `turnIndex` — ход внутри низкоуровневого запуска; ни один из них не является `run_id`. На `agent_start/end/settled` Pi не предоставляет отдельного стабильного идентификатора запуска. Внутренний идентификатор AgentRGB на время логического запуска допустим, но конкретный алгоритм пока не фиксируется.

В реальном G очередь обработана внутри текущего логического запуска, без дополнительного `agent_start` и промежуточного `agent_settled`. Код Pi допускает автоматические продолжения до окончательного settled. Реальные provider retry и compaction не воспроизводились; resume/fork не проверялись. Эти неизвестные сознательно не блокируют первую реализацию подтверждённого профиля, но не объявляются полностью проверенными.

Минимальный JSON-опыт подтвердил `agent_start`, `agent_end` и `agent_settled`. Поле `willRetry` присутствовало в JSON agent_end, но отсутствовало в extension agent_end того же запуска. Полная замена расширения JSON/RPC не подтверждена; RPC исследован по установленным типам и коду, без активного опыта. Для текущего CLI-профиля используется механизм расширения; альтернативная интеграция и транспорт не выбираются.

## Что проверяет технический прототип

### Для обоих источников

- стабильность `session_id` и возможность сформировать `run_id`;
- порядок событий при обычном завершении, ожидании, возобновлении, отмене и сбое;
- поведение при нескольких последовательных запусках в одном сеансе;
- поведение при аварийном завершении процесса;
- повторная доставка и события после завершения запуска;
- совместимость с Windows и влияние обновлений источника;
- обнаружение подтверждённой потери источника и восстановление актуального состояния после переподключения без произвольного тайм-аута работы;
- достаточный набор идентификаторов для идемпотентной обработки одного логического терминального факта.

### Для Codex

- достаточно ли `UserPromptSubmit` для `run_started`;
- позволяет ли выбранный интерфейс надёжно определить фактические начало и окончание ожидания разрешения;
- когда `Stop` означает окончательную остановку после возможного продолжения;
- есть ли структурированный терминальный признак ошибки запуска;
- какой канал — hooks или `notify` — надёжнее для каждого события.

### Для Pi

Фаза 02 завершена с указанным выше частичным профилем. Дальнейшие вопросы не расширяют автоматически MVP:

- появится ли однозначный источник пользовательского прерывания и независимой ошибки запуска;
- как ведут себя реальные provider retry/compaction, resume/fork и повторные низкоуровневые запуски;
- как обрабатывать вложенные UI prompts и гонки с окончанием запуска;
- как сформировать внутренний `run_id` и проверить восстановление после разрыва наблюдения;
- сможет ли JSON/RPC заменить расширение с тем же покрытием состояний.
