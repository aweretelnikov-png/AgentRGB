# Интеграции источников

Этот документ фиксирует предварительное соответствие структурированных событий Codex и Pi модели AgentRGB. Он не заменяет технический прототип: события, поля и поведение зависят от версии источника.

## Общие правила

- Используются только структурированные события и поля источника.
- Показываются только состояния, которые источник позволяет подтвердить достаточно надёжно; неполная поддержка лучше ложного сигнала.
- Текст запросов, ответов и транскриптов не анализируется и не пересылается.
- Событие жизненного цикла сеанса не считается запуском.
- Терминальное событие означает остановку запуска, а не успешность задачи.
- `error` создаётся только при явном структурированном признаке ошибки запуска агента.
- Ошибка интеграционного кода или доставки сообщения относится к диагностике AgentRGB.
- Таймер не служит доказательством ответа пользователя или выхода из `waiting`.
- Недоступность AgentRGB не должна влиять на выполнение источника; отправка событий работает по принципу best effort.

## Codex

Актуальная документация Codex Hooks перечисляет события `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PermissionRequest`, `Stop` и `Interrupt`. `PermissionRequest` возникает перед запросом одобрения, а `Interrupt` — при пользовательском прерывании активного хода в основном потоке. Форматы и покрытие должны проверяться на поддерживаемой версии Codex.

Источники:

- [Codex Hooks](https://developers.openai.com/es-419/docs/hooks)
- [Codex advanced configuration](https://developers.openai.com/es-419/docs/config-file/config-advanced)

### Предварительное соответствие

| Событие Codex | Сообщение AgentRGB | Уверенность | Примечание |
|---|---|---|---|
| `SessionStart` | `session_opened` | Подтверждено документацией, проверить поля | Регистрирует сеанс. Не означает `working`. Причины запуска и возобновления нельзя считать новым активным ходом. |
| `SessionEnd` | `session_closed` | Подтверждено документацией | Закрывает сеанс. Не означает `completed`. Нужно проверить поведение при аварийном завершении процесса. |
| `UserPromptSubmit` | кандидат на `run_started` | Требует прототипа | Событие подтверждает отправку запроса, но нужно проверить, достаточно ли его для начала фактического запуска и есть ли более точное событие в используемом интерфейсе Codex. |
| `PermissionRequest` | кандидат на `run_waiting` | Не подтверждено | Codex собирается запросить разрешение, но другой hook может автоматически разрешить или запретить действие. Событие само по себе не доказывает, что пользователь увидел запрос и Codex ждёт ответа. |
| окончание ожидания разрешения | кандидат на `run_resumed` | Не установлено | Не предполагается отсутствующее универсальное событие. Нужно экспериментально найти надёжно связанную пару начала и окончания ожидания в выбранном интерфейсе Codex. |
| `Stop` | кандидат на `run_completed` | Требует прототипа | `Stop` срабатывает при остановке активного хода, но hook способен запросить продолжение. Сигнал `completed` можно выпускать только после подтверждения окончательной остановки, не анализируя текст ответа. |
| `Interrupt` | `run_interrupted` | Подтверждено документацией | Срабатывает при пользовательском прерывании активного хода основного потока; не срабатывает для неактивного потока и субагентов. |
| структурированное событие ошибки запуска | `run_error` | Не установлено | В проверенной документации hooks не найдено однозначное универсальное событие ошибки всего запуска. До подтверждения адаптер не должен генерировать `error`. |
| `PreToolUse` / `PostToolUse` | нет прямого перехода | Подтверждено документацией | События отдельных инструментов не определяют состояние или результат всего запуска. Ненулевой код инструмента не равен `run_error`. |

Codex также поддерживает `notify`, но актуальная документация конфигурации описывает только `agent-turn-complete`. Это может быть запасным каналом завершения, однако он не покрывает полную модель и требует сравнения с hooks на Windows.

Точный `waiting` для Codex считается неподдержанным, пока прототип не подтвердит и начало, и окончание реального ожидания пользователя. Если выбранный интерфейс Codex не даёт обоих надёжных событий, адаптер первой версии не поддерживает `waiting`. Таймер или факт появления `PermissionRequest` не заменяет это подтверждение.

## Pi coding agent

Документация Pi Extensions описывает события жизненного цикла сеанса, низкоуровневых запусков агента и блокирующих UI-запросов. AgentRGB объединяет автоматические продолжения в один логический период работы. Для интеграции подходит расширение Pi: оно получает события внутри процесса и может отправлять минимальные нормализованные сообщения локальному AgentRGB. JSON event stream рассматривается как альтернативный путь для headless-сценария, но выбор не сделан.

Источники:

- [Pi Extensions](https://pi.dev/docs/latest/extensions)
- [Pi JSON Event Stream Mode](https://pi.dev/docs/latest/json)

### Предварительное соответствие

| Событие Pi | Сообщение AgentRGB | Уверенность | Примечание |
|---|---|---|---|
| `session_start` | `session_opened` | Подтверждено документацией | Регистрирует сеанс и не означает `working`. |
| `session_shutdown` | `session_closed` | Подтверждено документацией | Причины включают выход, перезагрузку, новый сеанс, возобновление и fork. Не означает `completed`. |
| первый `agent_start` после settled-состояния | `run_started` | Подтверждена основа, группировку проверить | Начинает логический период автоматической работы. Точный способ формирования `run_id` остаётся открытым. |
| повторный `agent_start` до `agent_settled` | нет нового логического запуска | Проектное правило на основе документации | Retry, compaction/retry и queued continuation продолжают текущий логический период, а не создают новый пользовательский `run`. |
| `ui_prompt_start` при активном логическом запуске | кандидат на `run_waiting` | Требует прототипа | Срабатывает для блокирующих UI prompt. Диалог расширения вне активной работы агента не переводит AgentRGB в `waiting`. |
| `ui_prompt_end` для связанного активного запуска | кандидат на `run_resumed` | Требует прототипа | Используется только как пара соответствующему `ui_prompt_start`; нужно проверить вложенность и гонку с `agent_settled`. |
| `agent_end` | нет терминального события AgentRGB | Подтверждено документацией | Завершает только низкоуровневый запуск. Pi может автоматически выполнить retry, compaction/retry или queued continuation. |
| `agent_settled` | кандидат на `run_completed` | Подтверждено назначение, итоговые причины проверить | Завершает логический период автоматической работы: Pi не должен продолжить его автоматически. Это не означает успех задачи. |
| отмена активного запуска пользователем | `run_interrupted` | Требует прототипа | Нужно найти структурированный признак отмены в extension API или событиях сессии и отличить его от прочих причин остановки. |
| структурированная ошибка запуска | `run_error` | Требует прототипа | `tool_execution_end.isError` относится к отдельному инструменту и не должен автоматически становиться ошибкой всего запуска. Нужен подтверждённый терминальный признак уровня агента. |
| `tool_execution_end.isError` | нет прямого перехода | Подтверждено документацией | Используется только как техническое событие инструмента; агент может обработать ошибку и продолжить. |

JSON event stream документирует `agent_start`, `agent_end`, события ходов, сообщений и инструментов. В нём нужно отдельно проверить наличие эквивалентов `agent_settled` и UI prompt событий для используемой версии; до этого поток нельзя считать полной заменой расширению.

Логический запуск Pi начинается первым `agent_start` и заканчивается соответствующим `agent_settled`. Повторные низкоуровневые `agent_start` и `agent_end` внутри этого интервала не создают новые пользовательские терминальные сигналы. Формирование стабильного `run_id` определит прототип.

## Что проверяет технический прототип

### Для обоих источников

- стабильность `session_id` и возможность сформировать `run_id`;
- порядок событий при обычном завершении, ожидании, возобновлении, отмене и сбое;
- поведение при нескольких последовательных запусках в одном сеансе;
- поведение при аварийном завершении процесса;
- повторная доставка и события после завершения запуска;
- совместимость с Windows и влияние обновлений источника;
- обнаружение подтверждённой потери источника и восстановление актуального состояния после переподключения без произвольного тайм-аута работы;
- достаточный набор идентификаторов для идемпотентной обработки одного логического терминального факта.

### Для Codex

- достаточно ли `UserPromptSubmit` для `run_started`;
- позволяет ли выбранный интерфейс надёжно определить фактические начало и окончание ожидания разрешения;
- когда `Stop` означает окончательную остановку после возможного продолжения;
- есть ли структурированный терминальный признак ошибки запуска;
- какой канал — hooks или `notify` — надёжнее для каждого события.

### Для Pi

- выдаёт ли `agent_settled` всю информацию, нужную для терминального события;
- как отличить пользовательское прерывание от других остановок;
- существует ли структурированная ошибка уровня запуска;
- доступны ли нужные события в JSON mode или требуется расширение;
- как корректно обрабатывать автоматические retry и compaction;
- как сгруппировать низкоуровневые запуски до `agent_settled` и сформировать стабильный `run_id`.
