## E: ручное прерывание инструмента

[Сырые события E](results/E-tui-20260920-192031-461/), 13 записей, `mode=tui`.
Пользователь подтвердил прерывание выполнявшегося инструмента штатным Escape.
Между tool_call и tool_result прошло 1,729 секунды вместо запрошенной 20-секундной
паузы; длительность сама по себе не используется как классификатор прерывания.

```text
session_start → input → before_agent_start → agent_start
→ turn_start(0) → tool_call(bash) → tool_result(isError=true)
→ turn_end(0) → turn_start(1) → turn_end(1)
→ agent_end(isIdle=false) → agent_settled(isIdle=true) → session_shutdown
```

По одному agent_start/end/settled. Отдельного события interruption в подписанном
наборе не было; разрешённые поля не содержат aborted/interrupted. Порядок типов,
число ходов и isError совпадают с F (различается инструмент). Использовать имя
инструмента или задержку для угадывания исхода нельзя. Поэтому в текущем профиле
наблюдения interrupted не поддерживается. Наличие скрытого от регистратора
stopReason в типах API не превращается в доказанную семантику отмены пользователя.
Наблюдение E также доказывает, что settled приходит после ручного прерывания:
его нельзя безусловно преобразовывать в completed.

[Сырые события G](results/G-tui-20260920-192140-600/), 21 запись, `mode=tui`.

```text
20 agent_settled               16:23:54.568Z  isIdle=true, pending=false
21 session_shutdown
```

Очередь действительно присутствовала во время активного запуска и была обработана
до settled. Дополнительный input не создал новый agent_start или before_agent_start.
Второй запуск состоит из двух ходов и одной пары agent_start/end. Ранний settled
№ 8 относится к отдельному первому запуску; его нельзя объявлять промежуточным
settled опыта очереди. `hasPendingMessages` объединяет очереди: лог не различает
steering и follow-up, поэтому конкретный вид очереди не утверждается.
На input pending ещё false, а на tool_result уже true: нельзя считать наличие
очереди подтверждённым непосредственно полем input до её фактической постановки.

Повторный низкоуровневый agent_start **до** settled здесь не воспроизведён.
Проверен дешёвый queued-сценарий; искусственные provider retry и compaction
не вызывались. Инвариант нескольких agent_start/end до одного settled остаётся
подтверждённым кодом, но не реальной retry/compaction-трассой.

## 02H. Extension, JSON и RPC

Это сравнение установленного кода и документации; активного RPC-опыта не было.
Минимальный активный JSON-опыт A выполнен. Отсутствие универсального события не трактуется как
невозможность построить другой канал.

В [JSON-опыте A](results/A-json-2026-09-20T16-15-41-548Z/) сохранены отдельно
extension trace и `wire-lifecycle.jsonl` с явно разрешёнными полями stdout.
Последовательность wire: `session → agent_start → turn_start → turn_end →
agent_end(willRetry=false) → agent_settled`. В extension trace того же процесса
`mode=json`, на agent_end нет willRetry, settled имеет isIdle=true. Сырой stdout
не сохранялся; содержание сообщений не анализировалось. Это фактическое
подтверждение разных проекций одного lifecycle, не альтернативный адаптер.

| Возможность | Extension | JSON | RPC |
|---|---|---|---|
| Начало работы | agent_start фактически в A/B/F и JSON A | agent_start фактически в JSON A | session.subscribe, код |
| Окончательный settle | agent_settled фактически в A/B/F и JSON A | agent_settled фактически в JSON A | Передаёт settled, код |
| Начало UI waiting | ui_prompt_start фактически в D, kind=custom | В print/JSON нет диалогового UI; универсальное waiting unknown | extension_ui_request для поддержанных диалогов; generic ui_prompt_start не пересылается этим каналом |
| Конец UI waiting | ui_prompt_end фактически в D, без причины и prompt id | unknown | Клиент отправляет extension_ui_response; это не универсальное подтверждение окончания UI со стороны агента; тайм-аут/abort также закрывают promise |
| Interruption | E неотличим от F по текущим полям; stopReason в сообщениях не читался | stopReason в сообщениях, проверка unknown | Команда abort и ответ на команду есть; stopReason в сообщениях, проверка unknown |
| Session lifecycle | session_start/shutdown фактически получены | Начальный session header фактически; полного эквивалента extension lifecycle в опыте нет | get_state/команды управления; полный эквивалент extension lifecycle unknown |

RPC не поддерживает произвольный TUI `ctx.ui.custom()` как полноценный интерфейс.
Следовательно, заменить CLI-расширение RPC без смены интерфейса пользователя
нельзя считать подтверждённым решением. JSON/RPC содержат полный пользовательский
контент: сырой поток не подходит для сохранения в AgentRGB без фильтрации.
Альтернативный адаптер не разрабатывался.

## Ответы на 12 вопросов

1. **working:** в A/B/F/D/E/G agent_start даёт isIdle=false; активность сохраняется
   до settled. По input/session_start/before_agent_start working не выпускать:
   перед обычным новым запуском на этих событиях isIdle=true. Дополнительный input
   во время G сам по себе не создаёт нового запуска. Retry ещё не проверен.
2. **waiting:** ui_prompt_start при активном логическом запуске; подтверждено D
   для ctx.ui.custom установленного ask_user_question в пользовательском CLI.
   D-idle подтверждает обязательность проверки активного запуска: UI events бывают и без него.
3. **Граница waiting:** эти события охватывают блокирующие select/confirm/input/editor/custom
   через ctx.ui. Обычный текстовый вопрос модели ими не покрывается. Произвольный
   ввод стороннего расширения в обход ctx.ui также не имеет гарантированного покрытия.
4. **Возврат:** парный ui_prompt_end при всё ещё активном запуске; в D после него
   реально продолжилась работа. Это подтверждённое основание для working в этом сценарии.
   Это не доказательство именно ответа пользователя; при уже завершённом запуске
   событие не должно вновь включать working.
5. **settled и completed:** settled — подтверждённая граница снятия активности, но не надёжный
   самостоятельный completed по существующей модели STATES.md. Он не различает
   причину прекращения работы; в E приходит после ручного Escape. Нельзя маскировать
   это расхождение архитектуры и API.
6. **interrupted:** структурированный aborted есть в типе stopReason; отдельного
   события прерывания среди ExtensionAPI.on нет. Ручной E выполнен, но его разрешённые
   поля не отличают отмену от F. Регистратор не читает сообщения. interrupted
   по текущему разрешённому списку не поддерживается.
7. **error:** структурированный stopReason=error существует на уровне сообщения;
   логическое завершение после retry отдельно не подтверждено. Ошибку отдельного
   инструмента не поднимать до ошибки запуска. Ошибка аутентификации до start
   не доказывает наличие run_error активного запуска.
8. **Повторные start/end:** код Pi допускает agent.continue() до единственного
   finally/settled. Queued follow-up может быть обработан внутри того же agent loop,
   не обязательно создавать ещё один agent_start. В G это подтверждено: очередь
   обработана внутри одной пары agent_start/end; повторный start до settled не наблюдался.
9. **Идентификаторы:** sessionId через sessionManager, turnIndex и toolCallId
   фактически получены в A/B/F/D/E/G. В G один sessionId сохраняется на двух
   самостоятельных запусках, а turnIndex снова начинается с 0. turnIndex сбрасывается
   на agent_start и не является глобальным run id. agent_start/end/settled и
   ui_prompt_start/end не предоставляют отдельного run/prompt id. Стабильность
   sessionId при resume/fork не проверена. AgentRGB run_id не изобретён.
10. **Достаточность extension API:** механизм пригоден для исследования; достаточность
    для полного адаптера ещё не доказана: E выявил недостаточность текущих полей
    для классификации терминального исхода.
11. **Полная замена JSON/RPC:** не подтверждена. Начало/settle реально получены в JSON,
    waiting и lifecycle различаются; RPC предполагает собственный UI-клиент.
12. **Что не поддерживать сейчас:** interrupted, error и безусловный completed.
    working подтверждён в A/B/F, waiting и возврат в working — в D. Текстовый вопрос
    модели, idle UI и таймер не служат основаниями для waiting.

## 02I. Предлагаемый автомат — не реализация

По A/B/F/D подтверждены `idle → agent_start → working → agent_settled → idle`,
без классификации терминального исхода. Вызовы инструментов и границы ходов
не меняют активности; даже инструментальная ошибка не закрывает запуск.

Для D подтверждена ветка working → waiting → working. E завершает активность
без отличимого исхода; G обрабатывает очередь без нового запуска. Предложение:

```text
idle -- первый agent_start --> working
working -- ui_prompt_start --> waiting
waiting -- ui_prompt_end, запуск ещё активен --> working
working/waiting -- agent_settled --> idle, терминальная причина ещё unknown
```

Повторный agent_start до settled не создаёт новый логический запуск.
UI вне запуска не активирует waiting. Поздний ui_prompt_end после settled
не возобновляет завершённый запуск. Соответствие settled → completed пока не принимается.
Переходы обычной активности и D подтверждены. E снимает активность через settled,
но не классифицирует прерывание. G подтверждает обработку очереди внутри запуска;
повторные низкоуровневые запуски при retry ещё не наблюдались.

## Узкий опыт stopReason

### Область и приватность

По отдельному заданию расширены только экспериментальный регистратор и его тесты;
добавлены реальные JSONL. Из документов изменён только этот RESULTS.md.
Основная архитектура, docs/, RGB и постоянная конфигурация Pi не менялись.

На turn_end записывается `message.stopReason`, на agent_end — stopReason последнего
assistant в `messages`. Для выбора читается только структурированный дискриминатор
`role`, который **не сохраняется**. Не читаются content, thinking, errorMessage,
тексты сообщений, аргументы и результаты инструментов. Объекты сообщений не
копируются и не сериализуются. Значение stopReason принимается только из enum
установленной версии; неизвестная строка не попадает в JSONL.

Уточнение к описанию первоначального регистратора в README: контейнеры
`turn_end.message` и `agent_end.messages` теперь просматриваются исключительно
для этого разрешённого метаданного; прежнее утверждение о полном отсутствии
их чтения относится к первому этапу. Сам README по текущему заданию не изменён.

Добавлен тест записи настоящего JSONL с приватными sentinel-строками и getters,
которые считают и запрещают чтение content/thinking/errorMessage/toJSON.
Проверяется, что ни приватные значения, ни поля сообщений не попали в файл;
число обращений к запрещённым getters равно нулю. Второй тест не допускает
подмены отсутствующей/неизвестной причины последнего assistant более ранним stop.
Всего пять тестов проходят.

### API установленного Pi 0.85.1

Версия повторно проверена по package.json. Использовались поставляемые типы
и реализация, а не документация latest.

1. `turn_end.message` содержит сообщение завершённого хода; также есть
   `message_end.message`. Для эксперимента нового message_end-подписчика не нужно.
2. `agent_end.messages: AgentMessage[]` содержит сообщения низкоуровневого запуска.
   StopReason доступен через последний элемент с `role === assistant`. Последний
   элемент массива вообще может быть toolResult; брать просто `messages.at(-1)` нельзя.
   Сам agent_settled не содержит сообщения или причины.
3. Enum StopReason: `pending | stop | length | toolUse | error | aborted | deferred`.
4. Один запуск может содержать несколько assistant с разными причинами. Реальный F
   ниже подтверждает `toolUse → stop`; промежуточная причина не является исходом запуска.
5. Предложение выбора: на agent_end брать только последний assistant, а окончательное
   решение откладывать до agent_settled. При повторном agent_start в том же логическом
   периоде прежний кандидат должен перестать считаться финальным. Следующий agent_end
   заменяет его, включая отсутствующее/неизвестное значение: откатываться к более
   раннему stop нельзя. При пропуске/ошибке регистратора классификация unknown.
   Это описание для будущего адаптера; автомат или нормализатор не реализованы.

TurnEndEvent), `pi-ai/dist/types.d.ts:287` (StopReason),

### E: ручное прерывание

[Первая попытка E](results/E-tui-20260920-195308-233/) дала
`turn_end(0, aborted) → agent_end(aborted) → agent_settled → session_shutdown`.
Пользователь подтвердил ручной Escape. В логе нет tool_call, поэтому это полезное
наблюдение отмены во время генерации, но не требуемый опыт отмены работающего инструмента.
Повтор после фактического старта инструмента выполнен.

[E во время инструмента](results/E-tui-20260920-195410-083/), TUI;
пользователь подтвердил выполнение ручного Escape по инструкции:

```text

→ turn_end(0, stopReason=toolUse) → turn_start(1)
→ turn_end(1, stopReason=error)
→ agent_end(stopReason=error) → agent_settled → session_shutdown
```

Это **не aborted**: JSONL содержит error на последнем turn_end и agent_end.
Факт ручного прерывания получен из действия/подтверждения пользователя, а не
угадан из длительности, имени инструмента, isError или числа ходов. Эти признаки
не используются для классификации. Не читался errorMessage или content.
Точная внутренняя причина представления отмены как error этим узким опытом
не установлена; выдавать предположение о провайдере за факт нельзя.

Сочетание A/F/E показывает: stopReason помогает отличить наблюдённое обычное
завершение от обеих отмен, но не даёт устойчивого отдельного значения для
пользовательского прерывания. `error → run_error` дало бы ложную классификацию
в опыте E, где пользователь явно прервал работу. Объединять aborted и error
в interrupted тоже нельзя: настоящая ошибка выполнения от этого не становится
действием пользователя.

Дополнительное ограничение по установленному коду: `ctx.abort()` доступен
расширениям (`extensions/runner.js:556`, `agent-session.js:2064`), а отмена
Agent использует общий AbortController (`pi-agent-core/dist/agent.js:202`).
Само поле stopReason не содержит инициатора отмены. Даже единичный aborted
не доказывает ручное действие в произвольном наборе расширений. Это вывод по
коду, не дополнительный эксперимент с программной отменой.

### Ответы на пять итоговых вопросов

1. **Normal completion:** да, в проверенных A/F: последний assistant имеет stop,
   затем приходит settled. Можно предложить completed для этого сочетания,
   без обещания успешности задачи. Это не универсальная аттестация всех провайдеров,
   расширений, retry/compaction и редких гонок отмены.
2. **Manual interruption:** в известных ручных опытах обычный stop отличился
   от aborted/error, но надёжной классификации именно пользовательского прерывания
   одним stopReason нет. E дал разные значения на разных стадиях, инициатор
   отмены полем не обозначен. interrupted первой версии пока не поддерживать.
3. **Run-level error:** надёжно не определён. Значение error действительно наблюдалось,
   но после ручного Escape. Это не отдельное подтверждение самостоятельной ошибки
   запуска; провайдер, сеть и авторизация искусственно не ломались.
4. **Терминальные сигналы первой версии:** предложить только completed, когда
   последний assistant последнего низкоуровневого запуска имеет stop и логический
   период завершился через settled. При отсутствии причины, разрыве наблюдения,
   aborted/error/length/toolUse/pending/deferred — без терминального сигнала.
   Причину прошлого запуска не переносить. Ничего из этого пока не реализовано.
5. **Неподдерживаемое:** interrupted и error; остальные перечисленные причины
   остаются неклассифицированными. working, waiting и окончание активности
   сохраняют подтверждённую поддержку. Терминальные сигналы не являются
   постоянными состояниями.

**Архитектурный инвариант:** agent_settled всегда означает только конец логической
активности: working/waiting → отсутствие активности. Completed — дополнительная
