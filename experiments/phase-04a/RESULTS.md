# Фаза 04A: Pi → HTTP → Core → FakeOutput

Даты: 21–22 сентября 2026 года (Europe/Moscow). Статус: **04A подтверждена**.
Реализация, автоматические проверки и живые A/B/C/Core-down выполнены.
Устройства не подключались.

## Среда и запуск

- Windows; Python 3.14.4; Node.js v24.15.0; Pi 0.86.1.
- Исследование фазы 02 относилось к Pi 0.85.1. Нужные типы событий и реализация
  UI lifecycle повторно прочитаны в установленном 0.86.1.
- Endpoint: `POST http://127.0.0.1:8765/v1/events`.
- Единственная настройка транспорта: `AGENTRGB_PORT`, одинаковая для обоих процессов.
- Только стандартные библиотеки Python/Node и уже установленный Pi.

Из корня репозитория:

```powershell
$env:PYTHONPATH = Join-Path $PWD 'src'
python -m agentrgb.server
```

В другом терминале:

```powershell
pi -e ./integrations/pi/agentrgb.ts
```

Воспроизводимый стенд сам запускает и штатно останавливает Core. Он отключает
сохранение сессий Pi, автозагрузку расширений, skills и context files; передаёт
расширения явно через `-e`. Для сценария B используется уже установленный
`@juicesharp/rpiv-ask-user-question`. Стенд сохраняет только технические логи.
Регистратор из фазы 02 используется исключительно стендом, не production-кодом.

```powershell
$piCli = Join-Path $env:APPDATA 'npm/node_modules/@earendil-works/pi-coding-agent/dist/bundle/cli.js'
node ./experiments/phase-04a/run.mjs A $piCli
node ./experiments/phase-04a/run.mjs down $piCli
./experiments/phase-04a/start-tui.ps1 -Scenario B
./experiments/phase-04a/start-tui.ps1 -Scenario C
```

B: увидеть вопрос, несколько секунд не отвечать, затем ответить, дождаться
окончания работы и выйти через `/quit`. C: во время выполнения нажать Escape,
дождаться остановки и выйти через `/quit`. Стенд не имитирует эти действия.
Если среде нужен прокси, он наследуется из окружения запускающего процесса.
Его адрес и настройки авторизации не сохраняются в репозитории.

## Структура и решения

| Файл | Ответственность |
|---|---|
| `src/agentrgb/protocol.py` | Валидация профиля 04A и неизменяемое событие |
| `src/agentrgb/state.py` | Реестр активных запусков, агрегирование, время сигнала, контракт вывода |
| `src/agentrgb/server.py` | Loopback HTTP, сериализация доступа к Core, штатное завершение |
| `src/agentrgb/fake.py` | Печать семантических команд без своей бизнес-логики |
| `integrations/pi/agentrgb.ts` | Pi extension: нормализация и ограниченная best-effort-доставка |
| `tests/` | Автомат, транспорт, приватность, классификация и отказы |
| `experiments/phase-04a/` | Стенд, технические трассы и этот отчёт |

Профиль использует имена архитектуры: `run_started`, `run_waiting`,
`run_resumed`, `run_ended`. `schema_version=1`, `source=pi`. Все девять полей
контракта обязательны; дополнительные поля запрещены. `metadata` пуст,
кроме необязательного `outcome` у `run_ended`: `completed` или `unknown`.
Отсутствующий outcome означает unknown. Остальные исходы отклоняются.
Timestamp содержит часовой пояс; идентификаторы — 1–128 ASCII букв, цифр,
дефисов или подчёркиваний. Pi adapter создаёт UUID для экземпляра, запуска
и события; session_id берёт из sessionManager.

HTTP принимает `Content-Type: application/json`, UTF-8, не более 4096 байт,
единственный Content-Length, без transfer/content encoding. Повторяющиеся
JSON-ключи отклоняются. В логах нет исходного body, URL или заголовков.
Валидное, но неуместное событие возвращает 200 с технической причиной игнорирования;
ошибка схемы — 400, тип содержимого — 415, превышение размера — 413.
При раннем отказе до чтения недопустимого тела Windows может закрыть соединение
с reset; клиент не должен рассчитывать на получение тела такого ответа.
На Windows сокет использует SO_EXCLUSIVEADDRUSE: второй процесс не может
привязаться к тому же endpoint. Немедленный повторный запуск после штатного
закрытия проверен отдельно.

Ядро различает полный ключ `(source, source_instance_id, session_id, run_id)`.
Один сеанс имеет один активный логический запуск; другой start в том же сеансе
отклоняется. Разные сеансы и экземпляры независимы. Приоритет:
`waiting > working > idle`. `completed` длится 2 секунды по monotonic clock;
tick сервера — каждые 20 мс, отдельно от чтения HTTP. Waiting немедленно
отменяет сигнал; пропущенные сигналы не повторяются. Следующий допустимый
completed другого запуска заменяет текущий и начинает свои 2 секунды.
После окончания сигнала агрегат вычисляется заново.

Дедупликация хранит последние 4096 event_id; такой же ограниченный список
закрытых ключей защищает от повторного start с новым event_id. Первый принятый
run_ended окончателен: последующие сообщения этого запуска не меняют исход.
После вытеснения обоих идентификаторов очень старый replay не гарантированно
распознаётся. Постоянного хранилища нет.

Операции выхода соответствуют архитектуре: acquire, show_activity, show_signal,
resume_activity, release. Для FakeOutput release печатает `OUTPUT idle`.
При исключении выхода Core пытается вызвать release; штатная остановка сервера
тоже освобождает выход. Аппаратное восстановление этим не подтверждается.

Pi читает только role и stopReason последнего assistant. На каждом agent_start
кандидат сбрасывается; на каждом agent_end полностью заменяется. Settled снимает
активность с completed только для последнего stop. Нет чтения текста сообщений.
Сетевой deadline — 200 мс от создания запроса; максимум 8 незавершённых отправок.
Один socket стандартного HTTP Agent сохраняет порядок конкурентных UI hooks.
Ожидание socket входит в тот же deadline. При переполнении событие теряется.
Нет прикладной очереди, retries, reconnect или ожидания восстановления Core.
Ответ Core не используется для управления Pi; его тело не читается.

## Автоматические проверки

```powershell
$env:PYTHONPATH = Join-Path $PWD 'src'
python -m unittest discover -s tests -v
node --test tests/pi-adapter.test.mjs
```

Итоговый набор: 19 Python-тестов и 10 Node-тестов. Покрыты заданные
переходы, агрегация, время и отмена completed, дубль terminal с новым event_id,
закрытый run, неверная последовательность, ограничение истории, освобождение
выхода при остановке и исключении, HTTP-валидация и зависший клиент.
У Pi проверены UUID, повторные starts, UI lifecycle, terminal classification,
запрет чтения приватных getters и сериализации sentinel, реальные HTTP-отправки,
отсутствующий/зависший/ошибающийся Core и некорректный HTTP-ответ. Пакет из
100 отправок зависшему Core завершается в пределах одного deadline с допуском
планировщика, без накопления ожиданий. Лимит незавершённых отправок снижен до 8:
при 32 Node выдавал предупреждение о числе listeners в искусственном burst.

Первоначальная фикстура зависшего HTTP-сервера не закрывала свои сокеты при
teardown. Фикстура исправлена: каждый сокет закрывается в finally; повторный
Node-прогон завершился без зависания. Это ошибка стенда, не наблюдение сбоя Pi.

## Живые опыты

### Первая попытка A: неизвестный исход

[Трасса Pi](results/A-2026-09-21T16-09-10-698Z/) и
[Core](results/A-2026-09-21T16-09-10-698Z/core.log):

```text
Pi: agent_start → agent_end(error)
    → agent_start → agent_end(error)
    → agent_start → agent_end(error)
    → agent_start → agent_end(error) → agent_settled
Core: run_started / OUTPUT working
      run_ended(outcome=unknown) / OUTPUT idle
```

Pi завершился с кодом 1. Повторные starts не создали лишних run_started;
completed отсутствует. Это не успешный A и не ручной Escape C.
HTTP_PROXY/HTTPS_PROXY в окружении отсутствовали; прежний опыт требовал прокси.
Причина stopReason=error по содержимому errorMessage не исследовалась.

### A: обычное завершение — подтверждено

[Трасса Pi и process.json](results/A-2026-09-21T21-00-23-740Z/) и
[Core](results/A-2026-09-21T21-00-23-740Z/core.log):

```text
Pi: agent_start → agent_end(stop) → agent_settled → session_shutdown
Core: run_started / OUTPUT working
      run_ended(outcome=completed) / SIGNAL completed
      OUTPUT idle
```

Pi завершился с кодом 0, без тайм-аута и диагностических категорий ошибки.
Использован переданный пользователем прокси только в окружении процессов;
его адрес в репозиторий не записан. Регистратор подтвердил последний stop,
а Core создал один completed и самостоятельно вернулся в idle.

### Core-down: невмешательство — подтверждено

[Трасса Pi и process.json](results/down-2026-09-21T21-00-36-290Z/):

```text
Core: не запущен; перед стартом проверен ECONNREFUSED на endpoint
Pi: agent_start → agent_end(stop) → agent_settled → session_shutdown
Process: exitCode=0, timedOut=false, diagnostics=[]
```

Pi с AgentRGB extension нормально завершил безопасный запрос. Потерянные
события не восстанавливались, повторов доставки и heartbeat нет.

### B: настоящее ожидание — подтверждено повтором

Первая [попытка B](results/B-2026-09-21T21-01-19-791Z/) завершилась с кодом 0.
Пользователь подтвердил появление вопроса, паузу перед ответом и выход через
`/quit`. UI span длился около 41,9 секунды. Но Core не получил run_started:
последующие run_waiting/run_resumed/run_ended получили unknown_run.
Между before_agent_start и записью agent_start прошло около 155 мс,
что согласуется с истечением прежнего deadline 150 мс. Точная причина потери
не установлена; сквозной B не засчитан. Deadline увеличен до разрешённых
заданием 200 мс, без retries.

[Повтор B: трасса Pi и process.json](results/B-2026-09-21T21-03-36-272Z/) и
[Core](results/B-2026-09-21T21-03-36-272Z/core.log):

```text
Pi: agent_start → tool_call(ask_user_question)
    → ui_prompt_start → ui_prompt_end
    → agent_end(stop) → agent_settled → session_shutdown
Core: OUTPUT working → OUTPUT waiting → OUTPUT working
      → SIGNAL completed → OUTPUT idle
```

Все четыре нормализованных события применены. Между применением run_waiting
и run_resumed прошло 21,767 секунды. Пользователь отдельно подтвердил,
что в повторном опыте увидел вопрос, ответил после паузы и вышел через `/quit`.
Pi завершился с кодом 0; ошибок стенда и тайм-аута нет.
Успешный повтор не доказывает отсутствие потерь при любой нагрузке:
ограничение best effort сохраняется.

### C: ручной Escape

[Трасса Pi и process.json](results/C-2026-09-21T21-04-59-184Z/) и
[Core](results/C-2026-09-21T21-04-59-184Z/core.log):

```text
Pi: agent_start → tool_call(bash) → tool_result(isError=true)
    → agent_end(error) → agent_settled → session_shutdown
Core: OUTPUT working → run_ended(outcome=unknown) / OUTPUT idle
```

Пользователь подтвердил Escape во время команды и последующий `/quit`.
Tool call зарегистрирован в 21:05:03.742 UTC, tool result — в 21:05:21.362 UTC.
Финальный stopReason — error, не aborted. Адаптер корректно не классифицировал
это как run-level error или interrupted. В логе нет SIGNAL completed.
Pi штатно закрылся с кодом 0, без тайм-аута стенда.

### Критерии 04A

| Критерий | Свидетельство | Результат |
|---|---|---|
| working | A, повтор B, C | Подтверждено |
| waiting | Повтор B, реальный ask_user_question | Подтверждено |
| waiting → working | Повтор B, ручной ответ | Подтверждено |
| completed → idle | A и повтор B | Подтверждено |
| unknown end → idle без completed | C, ручной Escape | Подтверждено |
| Core unavailable не ломает Pi | down, stop + settled, exitCode=0 | Подтверждено |

Последнее изменение production-кода — deadline 150 → 200 мс. После него
повторно прошли все 10 Node-тестов и живые B/C. A/down выполнены с 150 мс;
их повтор после изменения только лимита ожидания не проводился.

### Задержка доставки

Задержка доставки не измерена: технический регистратор вызывается после
адаптера, поэтому разница его timestamp с логом Core не является сетевой
задержкой. Deadline 200 мс — настройка, а не наблюдённое время доставки.

## Ограничения и следующий этап

- При потере run_ended состояние может остаться активным до перезапуска Core.
  Heartbeat/reconnect и семантические тайм-ауты намеренно отсутствуют.
- Нет гарантии доставки при падении Pi, перегрузке или остановленном Core.
- Нет remote access, UI, Codex, RGB, БД, конфигурационного framework.
- Retry с ошибками реально встретился в первой попытке A; успешные автоматические
  продолжения, compaction, resume/fork и гонки вложенных prompts не аттестованы.
- README и основная документация по прямому указанию не изменены. Их формулировки
  «код ещё не создан», «транспорт/run_id/outcome не выбраны» теперь требуют
  отдельного согласования. Здесь зафиксирован конкретный профиль 04A,
  без введения второго набора имён событий.
- До 04B критерии A/B/C/down выполнены. Реально необходимая работа для AULA:
  отдельный выходной адаптер с проверенными acquire/release и восстановлением
  профиля при ошибке, отмене и штатной остановке. Потребуется выбрать только
  подтверждённые аппаратные операции для семантических команд и проверить
  их с поддельным HID, затем отдельно на устройстве. FakeOutput не доказывает
  аппаратные гарантии. Retry/heartbeat и новая инфраструктура не требуются
  для перехода к ограниченному опыту 04B.

Предлагаемый 04B после подтверждения 04A: подключить прямой HID-выход AULA
через существующий контракт, ограничить изменения проверенными операциями
фазы исследования оборудования и отдельно проверить восстановление подсветки.
Автоматического подключения оборудования и коммита нет.
