# 04B: исследование нестабильного ответа `0x82`

23 сентября 2026 года. После остановки C1 выполнена только read-only
диагностика. **Изменяющих HID-команд: 0.** Production safety check не изменён;
C1, H2–H4 и 04C не запускались повторно.

## Сохранённый C1 raw против старых ответов

Источники: [старый полный 01B raw](../aula-f75-readonly/results/model-response-full.bin),
[C1 raw](results/C1-20260923T085100265865Z/get-001-response.bin),
[C1 API-диагностика](results/C1-20260923T085100265865Z/get-001.json),
[сравнение 11 полных raw](results/model-probe-20260923T085842180370Z/raw-comparison.json).
Три raw из предшествующего write-restore и baseline 04B совпали с 01B по всем
520 байтам. Старый SHA-256:
`40d4fc0f4a1091627643a59dfbfd42eab89749b55c6ea15031e04a8703196523`.
C1 SHA-256:
`cbd5e7fdcb6bc7637edb2dc8133cfe0d05c6388e12bc8fe662096659aeca8af5`.

| Абсолютный индекс полного report | Старый `0x82` | C1 `0x82` | Значение |
|---:|---:|---:|---|
| `[00]` | `06` | `06` | Report ID |
| `[01]` | `82` | `82` | Ответ на model query |
| `[02]` | `01` | `01` | Header |
| `[03]` | `00` | `00` | Header |
| `[04]` | `01` | `01` | Header |
| `[05]` | `00` | `00` | Header |
| `[06]` | `06` | `06` | Длина в header |
| `[07]` | `00` | `00` | Длина в header |
| `[08]` | **`03`** | **`06`** | Байт, трактуемый текущим parser как model |
| `[09]` | **`00`** | **`82`** | Неизвестное поле; изменилось вместе с `[08]` |
| `[10]` | `00` | `00` | Не изменился |
| `[11]` | `00` | `00` | Не изменился |
| `[12]` | `00` | `00` | PSD, старший байт |
| `[13]` | `CD` | `CD` | PSD, младший байт |

Полный побайтный diff **только `[08] 03→06` и `[09] 00→82`**; индексы
`[14..519]` совпали. C1 response имел валидный header и `GET_FEATURE`
API success. Необычная пара `06 82` в начале данных может быть следом
другого пакета/эхо, но происхождение по одному raw не доказано.

Путь parser:
`WindowsHid.get_feature` заполняет новый 520-байтный buffer с report ID
в `[0]`, получает полный raw, сохраняет его в диагностический sink до
валидации; `AulaF75Output.read(0x82)` вызывает `validate_response`.
Там после проверки 8-байтного header стоит буквальная проверка
`response[8] == 3` и `response[12:14] == 00 CD`.
C1 использовал тот же validator. Значит новое `06` действительно находится
по адресу model guard, а PSD по прежним адресам. Ошибка прибавления 8 к
offset здесь отсутствует. Поле `[9]` текущим parser не интерпретируется.

Два теста на сохранённых **реальных** 520-байтных raw прошли: старый принят,
C1 отклонён как `model_or_psd_mismatch`, побайтный diff и индексы проверены.
Parser ради тестов не исправлялся.

## Ограниченная свежая серия

[Сводка семи чтений и трёх открытий](results/model-probe-20260923T085842180370Z/summary.json).
Полные raw каждого `0x82`: `model-01.bin` … `model-05.bin` и `.hex` в том же
каталоге; для каждого есть `get-NNN.json` с timestamp, API success и SHA-256.
Устройство не получало write-команд состояния. Всего пять обычных
`SET_FEATURE 0x82 → GET_FEATURE`, затем один `0x84` и один `0x8A`.

| Цикл | Handle | `[8]` | `[9]` | PSD `[12..13]` | SHA-256 полного 520-byte ответа |
|---:|---:|---:|---|---|
| 1 | A | `03` | `00` | `00 CD` | `40d4fc0f…8703196523` |
| 2 | A | `03` | `00` | `00 CD` | `40d4fc0f…8703196523` |
| 3 | B, новый | `03` | `00` | `00 CD` | `40d4fc0f…8703196523` |
| 4 | B | `03` | `00` | `00 CD` | `40d4fc0f…8703196523` |
| 5 | C, новый | `03` | `00` | `00 CD` | `40d4fc0f…8703196523` |

Все пять ответов побайтно совпали со старым 01B raw. В короткой серии `03/06`
не чередовались; получение `03` не зависело от переоткрытия handle.
От C1 прошло отдельное время; причина единичного `06 82` неизвестна.
Дополнительные проверки или retry-policy из этих данных не следуют.

Для каждого открытия заново проверены VID `258A`, PID `010C`, интерфейс
`MI_01/COL06`, usage page `FF00`, usage `0001`, feature report 520 и
report ID `06`. Очищенный вид пути:
`HID#VID_258A&PID_010C&MI_01&COL06#<redacted>#<redacted>`.
SHA-256 полного нижнерегистрового пути одинаков на A/B/C:
`92461985de2fcf6166d2cb009b1fd6441fc38752d56d30da9e3f4395d216781e`.
Это подтверждает один Windows HID path **в нынешней серии**. В старых
экспериментах path hash и Container ID не сохранялись, поэтому совпадение
конкретного Windows instance/container с ними доказать нельзя; совпадает
сохранённая структурная identity интерфейса и обычный model raw. Системное
имя `Gaming Keyboard` для идентификации не использовалось.

## Config и color после серии

Интерфейс и PSD оставались прежними, поэтому на последнем handle прочитаны
ровно по одному `0x84` и `0x8A`. Полные
[config raw](results/model-probe-20260923T085842180370Z/config-response.bin) и
[color raw](results/model-probe-20260923T085842180370Z/color-response.bin)
прошли структурную валидацию. Оба 520-байтных ответа **побайтно совпали** с
восстановленным baseline ручного M1–M3. Config: `[66]=09`, `[67]=37`,
terminator `5A A5`; color `[29..31]=FF 00 00`, terminator `5A A5`.

## Решение об identity guard

Наблюдение C1 — не ошибка parser/offset, а единственный аномальный ответ
на прежнем наборе аппаратных признаков. Стабильное новое значение `06`
**не установлено**: свежие пять ответов снова `03`. Не доказано, что `[8]`
является вечным модельным идентификатором F75 при всех состояниях устройства;
также нет основания называть `06` другой моделью или принимать его для записи.

Текущий строгий `model == 03` остаётся **полезным обязательным guard для write**:
он корректно остановил C1 при несовпадении. Он может давать временный отказ
при аномальном ответе и не должен быть единственным доказательством identity.
Дополнительные обязательные признаки уже проверяются: точный VID/PID и vendor
HID collection, usage, feature size, валидные header/PSD `0x82`, валидные
`0x84`/`0x8A` и ожидаемое исходное состояние перед экспериментом.

Изменение production identity policy **сейчас не требуется и не предложено**:
ослабление `model == 03`, список допустимых `03/06` или автоматический retry
не поддержаны фактами. Отдельного diff с изменением policy нет, потому что
предложение — оставить её прежней; production safety check не менялся.
Данный read-only результат **не возобновляет C1** и не разрешает write.

Тесты: два новых real-raw теста и полный набор **80 Python-тестов прошли**.
Pi/Node и production не менялись, коммита нет.
