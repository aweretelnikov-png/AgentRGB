## Ограниченный аппаратный профиль

Разрешены запросы чтения `0x82`, `0x84`, `0x8A` и единственная изменяющая
операция `0x0A`. Write-report строится заново из 520 нулевых байт:
`[0]=06`, `[1]=0A`, `[7]=02`, RGB в `[29..31]`, `[0x202..0x203]=5A A5`.
Read-response не превращается в write-report заменой opcode.

Состояния отображаются фиксированными RGB: working `#0000FF`, waiting `#FFFF00`,
completed `#00FF00`. Idle означает release, отдельного цвета idle нет.
Effect, brightness, speed, flags, side light не записываются отдельными командами.
`effect=1` не трактуется как static. Неизвестные поля color profile не считаются
сохранёнными: ранее наблюдались изменения вне primary RGB при этой структуре report.

Конструктор выхода не открывает устройство. Acquire открывает единственный точно
подходящий интерфейс, проверяет его ещё раз на открытом handle, читает свежие
model/config/color и только после всех проверок допускает изменение.
Нет устройства, неоднозначность, неверные model/PSD/caps или некорректный
snapshot приводят к отказу без color write.

Одинаковый подтверждённый RGB повторно не отправляется. Нет software animation,
write polling, очереди цветов или retry/reconnect loop. Если текущий RGB уже
равен исходному и это подтверждено чтением, release не дублирует запись.

После успешного SetFeature с `0x0A` выход помечает состояние изменённым **до**
read-back. После каждого такого изменения проверяется primary RGB через `0x8A`.
При ошибке дальнейшая последовательность прекращается и выполняется одна
попытка restore исходного RGB. После restore тоже выполняется read-back,
включая попытку чтения после отказа SetFeature. Повторного restore нет.
Handle закрывается в finally; snapshot очищается.

Сбой первого SetFeature до подтверждённого изменения не вызывает restore.
Сбой последующей команды после предыдущего успешного изменения вызывает restore.
Неуспешный HID вызов сам по себе не доказывает, что аппаратное состояние осталось
неизменным; более сильной гарантии этот API не даёт.

`rgb_confirmed` означает лишь совпадение primary RGB при чтении. Это не визуальное
подтверждение и не full hardware profile restore. Если restore отправлен,
но read-back недоступен, статус `unverified`; при визуальном подтверждении
итог опыта может быть только partially confirmed.

## Ограничения и 04C

**Текущий подтверждённый output использует команды, которые могут сохранять
состояние в памяти клавиатуры.** Ограниченный опыт 04B проверяет техническую
жизнеспособность, но не безопасность неограниченных переключений в течение лет.
Ресурс flash не оценивался. До постоянной эксплуатации потребуется подтвердить
допустимый ресурс, найти volatile/runtime команду либо ограничить число writes.
Это не блокирует отдельно разрешённый ограниченный опыт.

Full hardware profile restore не обещается. Нет гарантий restore при forced kill,
аварии ОС, потере питания или физическом отключении устройства; watchdog не создан.
Синхронные Windows HID вызовы не имеют собственного deadline в этом backend;
адаптер не выполняет повторов. Другой RGB-контроллер не должен параллельно
перезаписывать профиль — аппаратная эксклюзивность не подтверждена.

Read-only диагностика после H1 выполнена и описана ниже. Не переходить к 04C
и не повторять H1 по оставшемуся бюджету.
После будущего успешного завершения H1–H4 предлагается 04C: отдельно согласованный короткий
сквозной опыт Pi → Core → AULA с ограниченным бюджетом writes и контролем
restore. Реальный Pi в 04B автоматически не запускается. Коммит не создан.

### Что изменено в диагностике

`WindowsHid.get_feature` сразу после API-вызова фиксирует sequence, UTC timestamp,
requested opcode, первые 8 байт предшествующего request, API success/failure,
размер буфера, исходный report ID, первые 32 байта response и `[0x202..0x203]`.
GetLastError читается немедленно и только при API failure; stale error при success
не используется. После failure сохраняется содержимое переданного буфера,
но оно не объявляется валидным ответом устройства.

Экспериментальный sink получает также полные response/request и сохраняет их
до возврата в `AulaF75Output.read` и до любого exception валидатора.
На `invalid_response_header` production-лог содержит фактические первые 16 байт.
Без sink production хранит только последнюю краткую диагностику в памяти
и не сохраняет полные reports на диск. В старом стенде H1–H4 sink тоже подключён,
но аппаратные сценарии сейчас запрещены и не выполнялись.

### Проверка ctypes boundary и последовательности H1

Microsoft задаёт для обоих вызовов `BOOLEAN (HANDLE, PVOID, ULONG)`;
длина буфера берётся из caps, а report ID задаётся первым байтом до GetFeature.
Сигнатуры Python сверены с этими определениями:
[HidD_GetFeature](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/hidsdi/nf-hidsdi-hidd_getfeature),
[HidD_SetFeature](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/hidsdi/nf-hidsdi-hidd_setfeature).

| Проверка | Наблюдение |
|---|---|
| Возврат | `c_ubyte` соответствует BOOLEAN; проверяется ноль/неноль |
| Аргументы | `wintypes.HANDLE`, `c_void_p`, `wintypes.ULONG`; ULONG — 4 байта, HANDLE имеет размер указателя |
| Calling convention | WinDLL, `use_last_error=True`; сигнатуры заданы явно |
| SetFeature buffer | Отдельный `c_ubyte[520].from_buffer_copy`, живёт весь синхронный вызов |
| GetFeature buffer | Каждый раз новый нулевой `c_ubyte[520]`, непосредственно перед вызовом `[0]=06` |
| Адрес | Передаётся адрес первого элемента массива; Python object/header не прибавляется |
| Signed bytes | Используется unsigned `c_ubyte`, затем неизменяемый `bytes` |
| Handle | `GENERIC_READ | GENERIC_WRITE`, sharing READ/WRITE, OPEN_EXISTING — как FeatureRead 01B |
| Aliasing | Write request, read request и GetFeature response — разные объекты; валидатор получает bytes ответа GetFeature |
| Жизнь handle | В 01B новый handle на каждый FeatureRead; Python держит один на acquire-cycle. Различие отмечено, но само по себе дефектом не доказано |

Статически путь H1: snapshot read завершает собственный GetFeature; blue создаёт
новый color report; следующий read создаёт новый read request; GetFeature создаёт
новый response buffer. Запись blue не используется как response и не передаётся
валидатору вместо прочитанного ответа. Производственных reopen, retries, sleep
после write и fallback query не добавлено.

Mock-тесты проверяют объекты и параметры на границе вызова, но не доказывают
поведение Windows driver/firmware. Дополнительное аппаратное свидетельство —
эта серия из девяти успешных чтений через настоящий backend, на одном handle.

### Фактические R1–R3

Перед R1 повторно подтверждены `258A:010C`, `MI_01/COL06`, `FF00/0001`,
feature 520, report ID 06, model 03, PSD 00CD, RGB `#FF0000`.
На это ушли три read-cycle: model/config/color. Затем:

| Опыт | Полных SET read request → GET циклов | Результат |
|---|---:|---|
| R1, `0x8A` | 1 | Валидный header, RGB `#FF0000`, terminator `5A A5` |
| R2, `0x8A` | 3 | Все три ответа побайтно идентичны R1, различий вне RGB — 0 |
| R3, `0x82` | 1 | Валидный header, model/PSD ожидаемые, совпадает со свежим model snapshot |
| R3, `0x84` | 1 | Валидный header/terminator, совпадает со свежим config snapshot |
| Всего с идентификацией | **9** | Все API success=true, handle закрыт |

SHA-256 всех четырёх color responses R1/R2:
`93f7fa0a46dc0c58f6bb5a117da5bd146a0933a598d48361c8425a0b51f286b5`.
Начальный color snapshot имеет тот же hash. Header во всех пяти:
`06 8A 01 00 01 00 00 02`; `[29..31]=FF 00 00`; `[514..515]=5A A5`.
Меняющихся байтов во всём 520-байтовом response нет.

Bare GET **пропущен**: исходный invalid header H1 неизвестен, сопоставлять его
с возможным noise нечем. Все чтения имеют отдельный предшествующий read request.
Стенд запрещает bare GET, любые state-write opcodes и более девяти read requests.

### Регрессионные проверки и вывод

Добавлено 10 тестов `tests/test_hid_diagnostics.py`: сохранение невалидного raw
до валидации/exception и фактических первых байт; API failure с GetLastError;
отсутствие чтения stale error при success; нулевая инициализация и report ID;
совпадение requests с 01B; отсутствие aliasing/знакового преобразования;
единственный restore после simulated change; отсутствие write/retry при ошибке
без change; отказ от noise с правдоподобным RGB; блокировка write/bare GET;
проверка ctypes signatures без открытия устройства. Несколько свойств проверяются
в одном тесте. **Все 57 Python-тестов прошли**, включая прежние 47.
Node/Pi adapter не менялся, его тесты в этой диагностике не перезапускались.

Уверенно установлен недостаток прежней диагностики: raw H1 терялся до фиксации
ошибки. Он устранён, но это не объясняет происхождение невалидного ответа.
Признаков локального buffer/signature bug не найдено. Обычный read transport
в этой небольшой серии стабилен; редкие сбои за её пределами не исключены.

Приоритетная гипотеза — особенность обмена непосредственно после `0x0A`.
Уверенность **низкая**: один исторический сбой без raw и отсутствие повтора
при девяти reads не устанавливают причинную связь. Конкретная причина firmware,
timing или возврата другого типа report не доказана.

Если продолжать физическую диагностику, минимальный отдельный опыт:
fresh identify/snapshot → одна blue write → диагностированный полный read-back
→ один restore → диагностированный restore read-back. Максимум **2** `0x0A`,
с сохранением raw до проверки независимо от результата и без retries.
На момент окончания R1–R3 этот опыт не был выполнен и требовал нового
отдельного разрешения. Последующее разрешение и фактический D1 описаны ниже.

## Единственный post-write диагностический опыт D1

Пользователь отдельно разрешил максимум две изменяющие команды: blue и
restore исходного `#FF0000`. Опыт выполнен один раз, без H2–H4 и без 04C.
[Сводка](results/D1-20260922T060817974854Z/summary.json),
[порядок операций](results/D1-20260922T060817974854Z/trace.json),
[побайтные сравнения](results/D1-20260922T060817974854Z/comparison.json).

Перед записью заново подтверждены VID/PID `258A:010C`, `MI_01/COL06`, usage
`FF00/0001`, feature 520, report ID 06, model 03, PSD 00CD и snapshot RGB
`FF 00 00`. Blue и restore reports отдельно сохранены как
`write-001-report.bin` и `write-002-report.bin` **до** соответствующего SetFeature.

После blue сразу выполнен обычный `SET_FEATURE 0x8A → GET_FEATURE`.
До этого чтения нет искусственного sleep, reopen, bare GET, retry или
дополнительного SET. Raw сохранён до валидации. Только после валидного ответа
стенд оставил три секунды для визуального наблюдения, затем выполнил restore.

### Первый ответ после blue

[Raw 520 байт](results/D1-20260922T060817974854Z/get-004-response.bin),
[диагностика](results/D1-20260922T060817974854Z/get-004.json).

Первые 32 байта (две строки по 16):

```text
06 8A 01 00 01 00 00 02 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 FF
```

- Header валиден: `06 8A 01 00 01 00 00 02`.
- `[29..31] = 00 00 FF`, `[0x202..0x203] = 5A A5`.
- API success=true; GetLastError при success не считывался.
- Sequence 4, UTC `2026-09-22T06:08:18.142107+00:00`.
- SHA-256: `4c2fc4acde52d209c36865727ed50153165c9e4d13b9102ceecb2528d8a834e4`.

С отправленным blue write-report ответ различается ровно в трёх байтах:
`[1]: 0A → 8A`, `[2]: 00 → 01`, `[4]: 00 → 01`. Следовательно, это валидный
color read-response с подтверждённым синим RGB, а не неизменённое эхо write.
С model response различается 8 байт, с config — 91, с color snapshot — только
два байта RGB. Ни один из этих полных пакетов не совпадает с post-blue response.
Ответ содержит 8 ненулевых байт и 512 нулевых: нули соответствуют наблюдаемому
разреженному color profile, сами по себе не означают неинициализированный buffer.
С полностью нулевым buffer совпадения нет; с начальным Get buffer `06 + 519 нулей`
тоже нет. Его полноценные header, RGB и terminator прошли строгую проверку.

### Restore и визуальное наблюдение

Единственный restore `0x0A #FF0000` отправлен успешно. Затем один обычный
read cycle дал валидные header/terminator и `[29..31] = FF 00 00`.
[Raw restore response](results/D1-20260922T060817974854Z/get-005-response.bin),
[его диагностика](results/D1-20260922T060817974854Z/get-005.json).

SHA-256: `93f7fa0a46dc0c58f6bb5a117da5bd146a0933a598d48361c8425a0b51f286b5`.
В этом опыте весь color response после restore побайтно совпал со свежим
color snapshot. Это не доказывает восстановление всего неизвестного аппаратного
профиля или других блоков устройства.

Ответ пользователя: «Синий не успел увидеть, исходная подсветка восстановилась».

| Изменяющие `0x0A` | **2 попытки, 2 успешных SetFeature**: blue + restore |
| Read requests / GetFeature | 5 / 5: snapshot model/config/color, post-blue, post-restore |
| Retry / bare GET / reopen между blue и read | 0 / 0 / 0 |
| Restore attempts | Ровно 1 |
| Handle | Закрыт |

| Тесты перед D1 | Все 57 Python-тестов прошли, включая mock D1 |

Для нового стенда добавлены SHA-256 и RGB в JSON диагностики, сохранение
отправленных write reports и отдельное имя D1 с лимитом 2. Production-тайминги,
валидация, retry-политика, Pi adapter и семантика Core не изменены.

### Объяснение прежнего сбоя и следующий шаг

Прежний `invalid_response_header` **не воспроизведён**. Немедленный первый
post-write read может быть валиден без workaround. Наиболее правдоподобная
рабочая версия прежнего события — разовый сбой/несоответствие возвращённого
report в обмене после write, с низкой уверенностью. Его конкретный вид неизвестен:
у старого H1 нет raw, а новые успешные байты не объясняют задним числом старый сбой.
Доказательств обязательного sleep, retry или reopen нет; они не добавлены.

Дополнительный физический повтор именно этой диагностики перед H2 сейчас
не обоснован: первый read и restore подтверждены, диагностика сохраняется.
В отдельно разрешённом H2 можно проверить визуальные цвета с заранее
согласованным наблюдением и прежней остановкой при первом отклонении.
Это не объявляет read transport безусловно стабильным. На момент завершения
D1 H2–H4 ещё не выполнялись; последующий отдельно разрешённый H2 описан ниже.
