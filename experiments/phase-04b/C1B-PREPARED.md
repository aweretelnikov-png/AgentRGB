# 04B-C1B: подготовка без физических записей

23 сентября 2026 года. Экспериментальный `c1b.py` разделяет опыт на обычные
неинтерактивные команды `prepare`, `apply-blue`, `restore` и `status`.
Production `AulaF75Output` не менялся. `prepare` выполнен только с read-only
запросами `0x82`, `0x84`, `0x8A`; изменяющих HID-команд пока **0**.

Текущая транзакция: `211d9c08-8c80-44e3-b5fd-8c784d524fd3`.
[Маркер](results/C1B-211d9c08-8c80-44e3-b5fd-8c784d524fd3/transaction.json)
имеет статус `prepared`, пустой список `writes`; handle закрыт.
[Полные raw и snapshot](results/C1B-211d9c08-8c80-44e3-b5fd-8c784d524fd3/)
сохранены до применения изменений.

| Fresh read-only baseline | Значение |
|---|---|
| HID | `258A:010C`, `MI_01/COL06`, usage `FF00/0001`, feature 520, report ID `06` |
| Windows interface path | SHA-256 `92461985de2fcf6166d2cb009b1fd6441fc38752d56d30da9e3f4395d216781e`; сам путь не сохранён |
| `0x82` | Валиден; model `03`, PSD `00CD`; SHA-256 `40d4fc0f4a1091627643a59dfbfd42eab89749b55c6ea15031e04a8703196523` |
| `0x84` | Валиден; `[66]=09`, `[67]=37`; SHA-256 `5a90dd25a6dd82b2d639193ba2e03d9e3d98ae909dad32531ae0a1924cd413e0` |
| `0x8A` | Валиден; RGB `[29..31]=FF 00 00`; SHA-256 `93f7fa0a46dc0c58f6bb5a117da5bd146a0933a598d48361c8425a0b51f286b5` |

Это тот же восстановленный baseline, что и после C1. Перед будущим
`apply-blue` стенд снова открывает устройство, выполняет **один свежий**
`0x82 → 0x84 → 0x8A` gate, сравнивает ответы с сохранённым baseline и только
после этого допускает запись. При отклонении запись не выполняется.

План для этой транзакции — не более четырёх изменяющих команд:

1. `0x04`: полный свежий config payload, только report `[67] 37→30`;
   затем один `0x84` с проверкой всего ожидаемого ответа.
2. `0x0A`: `#0000FF`; затем один `0x8A` с проверкой RGB. Успешный
   `apply-blue` завершается с открытой транзакцией и выводит
   `C1B_APPLIED_BLUE_RESTORE_REQUIRED`, чтобы цвет можно было увидеть.
3. Отдельная фаза `restore`: `0x0A → #FF0000` и один `0x8A`.
4. `0x04`: полный config из snapshot текущей транзакции; затем `0x84` и
   `0x8A` с побайтным сравнением с baseline. Успешный restore закрывает
   маркер; повторный restore не обращается к HID.

[Офлайн-просмотр четырёх подготовленных reports](results/C1B-211d9c08-8c80-44e3-b5fd-8c784d524fd3/preview.json)
показывает, что два config reports различаются только по `[67]`. Это расчёт
без отправки HID-команд, а не результат физического C1B.

Fake-HID сценарии проверили успешную открытую транзакцию, восстановление из
её snapshot, idempotent restore, частично изменённое состояние, ошибки после
config/blue, stale snapshot, другой device path, изменение model, отсутствие
stdin и предел четырёх записей. Все **92 Python-теста** прошли. В `restore` валидируются
model `03` и PSD `00CD`, но не требуется побайтное совпадение всего `0x82`:
это оставляет возможность безопасного восстановления при изменении иных
байтов ответа.

Физический `apply-blue` **не запускался**. Визуальное появление синего и
полный физический цикл `acquire → render → release` пока не подтверждены.
H2–H4, Pi и 04C не запускались; коммита нет. Следующий шаг требует отдельного
разрешения на изменяющие HID-команды именно этой транзакции.
