# 04B-C1: остановка на свежей идентификации

## Повторная попытка C1: config подтверждён, blue не выполнялся

Позднее 23 сентября 2026 года пользователь отдельно разрешил один повтор
C1 после read-only исследования model. [Сводка повторной попытки](results/C1-20260923T090447213540Z/outcome.json),
[raw после config change](results/C1-20260923T090447213540Z/after_config-response.bin),
[сводка однократного restore](results/C1-20260923T090447213540Z/abort-restore/summary.json).
Раздел ниже описывает предыдущую попытку, остановленную на `0x82`.

Новый свежий identity gate прошёл: VID/PID `258A:010C`, `MI_01/COL06`,
usage `FF00/0001`, feature 520, report ID 06, model `03`, PSD `00CD`.
Валидные `0x84` и `0x8A` побайтно совпали с восстановленным baseline:
config `[66]=09`, `[67]=37`, primary RGB `FF 00 00`.

Первая изменяющая команда — один `0x04` с полным свежим config payload
и единственным изменением report[67]/payload[59] `37→30`.
Один обычный `0x84` read-back прошёл валидацию; полный response отличается
от fresh config только в этом байте. Пользователь отдельно подтвердил в чате
одноцветный красный.

Интерактивный процесс ожидал ввод `RED` в отдельном PowerShell-окне, которое
пользователь не видел. Ответ в чате не поступал на stdin процесса. Согласно
правилу навыка computer-use, терминал нельзя автоматизировать через Windows UI.
Процесс остановлен, его HID handle освобождён; blue не запускался.
Чтобы восстановить единственное изменённое состояние, другой процесс
заново прочитал `0x84` и `0x8A`: config всё ещё отличался только `[67]=30`,
color profile побайтно совпадал с baseline. Затем отправлен **ровно один**
`0x04` restore из полного исходного свежего config. После него `0x84` и
`0x8A` побайтно совпали с baseline; handle закрыт. Пользователь подтвердил
исходный переливающийся профиль визуально.

| Этап | Результат |
|---|---|
| Fresh identity | Полностью совпала с обязательным baseline |
| Config acquire `0x04` | 1 успешная запись `37→30` |
| Config read-back | Валиден; единственное отличие — report[67] |
| Визуальное состояние | Одноцветный красный подтверждён пользователем |
| Blue `0x0A`, `0x8A`, визуально | Не выполнялись из-за недоступного окна |
| Color restore `0x0A` | Не нужен: blue write не было, исходный color profile подтвердился до/после |
| Config restore `0x04` | 1 успешная запись полного исходного payload |
| Финальный `0x84` | Полный 520-byte response побайтно равен baseline |
| Финальный `0x8A` | Полный 520-byte response побайтно равен baseline |
| Финальный вид | Исходная переливающаяся подсветка подтверждена пользователем |
| Изменяющие команды | **2 успешных `0x04` из лимита 4**, `0x0A`: 0 |

Это подтверждает работу config acquire `37→30` и доступное восстановление
пользовательского профиля. Механизм **`acquire → render blue → release`
не подтверждён**, потому что blue не выполнялся. C1 не повторяется в этом
допуске; H2–H4 и 04C не запускались. Production и Pi/Node не менялись,
коммита нет. Перед аппаратной работой прошли все 80 Python-тестов.

23 сентября 2026 года. Разрешённый цикл C1 начал свежий snapshot
`0x82 → 0x84 → 0x8A`, но остановился на первом ответе `0x82` до любой
изменяющей команды. Лимит четырёх записей не использован.

[Сводка](results/C1-20260923T085100265865Z/summary.json),
[диагностика первого GET](results/C1-20260923T085100265865Z/get-001.json),
[полный raw, 520 байт](results/C1-20260923T085100265865Z/get-001-response.bin).

Fresh identity интерфейса прошла по `258A:010C`, `MI_01/COL06`, usage
`FF00/0001`, feature 520 и report ID 06. Запрос чтения был обычный
`SET_FEATURE 0x82` с header `06 82 01 00 01 00 06 00`, затем один
`GET_FEATURE`; API сообщил success. Ответ сохранился до валидации.

Первые 16 байт ответа:

```text
06 82 01 00 01 00 06 00 06 82 00 00 00 CD 00 00
```

Header совпал с ожидаемым. PSD `[12..13] = 00 CD` совпал. Поле model
`[8] = 06`, тогда как ожидается `03`; `[9] = 82` вместо прежнего `00`.
Именно эти два байта отличаются от последнего подтверждённого полного
baseline model response. SHA-256 нового ответа:
`cbd5e7fdcb6bc7637edb2dc8133cfe0d05c6388e12bc8fe662096659aeca8af5`.
Это неожиданный ответ, но его причина неизвестна. Он не доказывает изменение
model устройства или дефект протокола; проверка baseline требует остановки.

| Показатель | Факт |
|---|---|
| `0x82` request / GetFeature | 1 / 1, API success |
| `0x84`, `0x8A` | Не выполнялись после отклонения |
| Изменяющие `0x04`, `0x0A` | **0** |
| Restore | Не нужен: AgentRGB не менял состояние |
| Handle | Закрыт |
| Визуальные этапы | Не начинались |
| Core/listener | Не запускались |

Стенд C1 ограничивает порядок и бюджет записей, сохраняет raw до валидации
и проверяет полное совпадение model/config/color с прежним baseline до первой
записи. В тестах проверены успешная ветка, отклонения на red/blue,
несовпадение config read-back и запрет записи при отличающемся baseline.
Отдельные 5 тестов C1 прошли; общий повторный прогон — **78 passed**.
Первый общий прогон дал единичный `ConnectionAbortedError` в локальном
HTTP-тесте, повторный прогон прошёл полностью. Этот сбой не относился к HID.

C1 **не проведён** и механизм управляемого цвета пока не подтверждён.
H2–H4 и 04C не запускались; production и Pi/Node не менялись. Коммитов нет.
Следующее действие требует отдельного решения по неожиданному `0x82`;
в пределах C1 повторов чтения и дополнительных опытов не было.
